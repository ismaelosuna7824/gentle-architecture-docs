# Architecture docs

Documentation that lives in the repository, in Markdown with Mermaid diagrams, and stays true because every claim points at the code it describes. Run the command the user asked for; with no command, infer it (a decision just made → `adr`; "document X" → `feature`; after edits → `update`).

Commands, as the text after `/skill:architecture-docs`:

| Command | Does |
|---|---|
| `init` | Map the repository and create the structure, the index and every document it can ground in code. |
| `adr <title>` | Record a decision from the current conversation. |
| `feature <name>` | Document one feature: components, data, states, flows. |
| `update` | Bring the docs in line with what changed in the code. |
| `check` | Report stale docs, broken links and invalid diagrams; change nothing. |

## Rules (always)

1. **Ground every statement.** Name the file, symbol or command it comes from (`src/payments/service.ts:PaymentService.capture`). Read the code before writing about it; never describe code you have not opened.
2. **Never invent numbers or policy.** SLOs, latency targets, retention, scale limits, roles and permissions, costs, compliance scope: take them from the code, config or the user. If none says, write the question under **Open questions** in that document and leave the value as `TBD (owner: …)`.
3. **Mark inference.** Anything deduced rather than read (intent, why a module exists) goes in as `> Inferred: …` so a human confirms or corrects it.
4. **Generate what can be generated.** API contracts, ERDs and schema tables come from the source of truth (OpenAPI generators, ORM schema, migrations). Mark generated files at the top: `<!-- generated by <tool/command>; do not edit by hand -->`, and say how to regenerate them.
5. **One fact, one place.** Link instead of copying. The glossary defines terms; other docs link to it.
6. **Match the project.** Write in the language the existing docs (or README) use; follow its naming and folder conventions if it already has docs.
7. **Diagrams are Mermaid** inside fenced ` ```mermaid ` blocks, using `flowchart`, `sequenceDiagram`, `stateDiagram-v2`, `erDiagram` and `classDiagram` only (they render everywhere: GitHub, editors, Gentle Shell GPUI). Draw C4 levels with `flowchart` and subgraphs, not Mermaid's experimental `C4Context` syntax. Keep one idea per diagram, under ~25 nodes. No emoji in diagrams: native renderers draw them as empty boxes.
8. **Small, reviewable changes.** Docs change in the same PR as the code they describe. Never delete a human-written section; mark it stale instead.

## Where things go

System-wide documents by type; anything that belongs to a single feature in that feature's folder. Read `references/structure.md` for the full tree and what each file holds.

```text
docs/
├── README.md            the map
├── glossary.md
├── architecture/        c4-context, c4-containers, deployment, nfr
├── adr/                 NNNN-title.md (global numbering)
├── security/            auth, data-classification, threat-model
├── operations/          local-setup, deploy-and-rollback, config, errors, runbooks/
├── api/                 generated contracts
└── features/<name>/     README (C4 level 3), data, states, flows
```

## Front matter (every document)

```yaml
---
title: Payments — states
owner: payments-team            # who answers questions about it; TBD if unknown
sources:                        # code this document describes; changes here make it stale
  - src/payments/**
  - prisma/schema.prisma
verified: 7d9fad6               # commit at which a person or agent last checked it against sources
status: current                 # current | stale | draft
---
```

`verified` is the short hash of `git rev-parse --short HEAD` when you finish checking the document. Generated files skip the front matter and use the generated marker instead.

## Commands

### init

1. Explore: README, package manifests, entry points, framework, config and env files, infrastructure (Dockerfile, compose, Terraform, CI workflows), database schema or migrations, API routes, existing docs and ADRs. List the containers (deployables) and the features (business capabilities, usually top-level modules).
2. Propose the plan to the user before writing: the documents you will create, the features you found, what you can generate, and the questions you need answered. Wait for confirmation unless the user said to proceed.
3. Create the structure from `references/structure.md`, filling each document from `references/templates/`. Fill only what you can ground; everything else is `TBD` plus an Open question.
   Track the units (an area or a feature each) in your task list and keep it current as they land: the person following along sees progress only through it. If you hand units to subagents, launch one batch per call, a few units at most, and mark the batch's tasks done (or blocked, with the reason) as soon as it returns, before launching the next. Never run the whole plan inside one long script: the list cannot change until the script ends.
4. Write `docs/README.md` last: what the project is, how to run it locally, and a link to every document with one line each.
5. Run `node scripts/docs-check.mjs` from the repository root (path relative to this skill) and fix what it reports.
6. Report: documents created, what is generated and how to regenerate it, the open questions grouped by owner.

### adr <title>

1. Number it: the next `NNNN` after the highest in `docs/adr/` (start at `0001`). File name: `NNNN-kebab-title.md`.
2. Fill `references/templates/adr.md` from the conversation: context (the forces at play), the decision, alternatives considered with why each lost, consequences (good and bad), and the features it affects. Ask for anything the conversation does not settle; do not fill alternatives nobody discussed.
3. Status `proposed` unless the user says it is decided (`accepted`). An ADR that replaces another sets `superseded by NNNN` on the old one; never rewrite an accepted ADR's decision.
4. Add it to the ADR list in `docs/README.md`.

### feature <name>

1. Find the feature's code and read it: entry points, services, data access, state fields and enums, events, external calls.
2. Write `docs/features/<name>/` from the templates:
   - `README.md`: what it does, who uses it, its components (C4 level 3 flowchart), its external dependencies, links to the rest.
   - `data.md`: an `erDiagram` of its entities plus the data dictionary (field, type, meaning, valid values, units, who writes it). For money: currency, precision, rounding rule and where rounding happens.
   - `states.md`: one `stateDiagram-v2` per entity with a lifecycle (status/state fields, enums), every transition with its trigger and guard, plus a table of the code that performs each transition. Flag transitions the code allows but the diagram's intent forbids (or the reverse) as findings.
   - `flows.md`: a `sequenceDiagram` per critical flow, including failure paths and retries.
   Skip a file the feature has no material for, and say so.
3. Link it from `docs/README.md` and add new terms to `docs/glossary.md`.

### update

1. Find what changed: `git diff --name-only <base>...HEAD` (base: the PR's target branch, else `main`/`master`), plus uncommitted changes.
2. Run `node scripts/docs-check.mjs --json` to get every document whose `sources` match those changes.
3. For each: re-read the changed code, update the document, set `verified` to the current commit and `status: current`. If a change contradicts an accepted ADR, do not edit the ADR: tell the user a new ADR is needed.
4. New feature folders, endpoints, entities or env vars without docs: create or extend the matching document.
5. Report what changed and what still needs a human.

### check

Run `node scripts/docs-check.mjs` and report its findings grouped by document, with what to do about each. Change nothing.

## Templates and references

- `references/structure.md`: the tree, what each file holds, and who reads it.
- `references/templates/*.md`: one per document type (adr, c4-context, c4-containers, feature, data, states, flows, deployment, deploy-and-rollback, nfr, auth, data-classification, threat-model, runbook, local-setup, config, errors, glossary, docs-readme).
- `scripts/docs-check.mjs`: staleness (sources changed since `verified`), missing front matter, broken relative links and malformed Mermaid fences. `--json` for machine-readable output, `--base <ref>` to compare against a branch instead.
